transport: cloudflare tunnel
     note: warning: until you put cloudflare access in front of agent.example.org (an owner step below), anyone on the internet can reach that hostname, and only the SSH keys of agent stand in the way. do that before you give the hostname to anyone.
     note: the tunnel routes exactly one hostname, agent.example.org, to this machine's SSH server (ssh://localhost:22), whatever the level; every other name gets 404. no other port, no private network route.
   30. give the installer one Cloudflare API token, once (owner, by hand)
       Cloudflare dashboard, My Profile, API Tokens: create a token with the permissions Account, Cloudflare Tunnel, Edit and Zone, domain name records, Edit (and Zone, Zone, Read, unless you give the zone number in SIRVEN_CLOUDFLARE_ZONE_ID), limited to your one account and the one zone of agent.example.org. never a token that can do anything else.
       hand it over one of two ways, and it is the only interactive step:
         in a file, the safer way and the one to use first: save it as /etc/sirven/cloudflare-api-token, owned by root, mode 0600, with one name only (no hard link) and no extra access control list; it is removed after the tunnel is made, so give it again to take the tunnel away. this is the only way that never puts the token in an environment.
         in the environment: set SIRVEN_CLOUDFLARE_API_TOKEN in your shell and run sudo --preserve-env=SIRVEN_CLOUDFLARE_API_TOKEN. sudo allows that only when its policy does. the installer takes the token out of its environment at once and hands it only to the steps that need it, but it cannot scrub the block of the environment it was started with: root can still read it in /proc/<installer process number>/environ until the installer ends, and the few commands the root gate runs before that (uname, the check of the folder it reads from, dirname) are started with it too.
   31. put cloudflare access in front of the hostname, with a service token (owner, by hand)
       cloudflare dashboard, access, applications: add agent.example.org as a self-hosted application.
       policy action: service auth, allowing only a new service token for your agent client.
       do not add email code login or any other login method.
       (until you do, the hostname is reachable by anyone, and only the SSH keys of agent stand in the way. do this before you give the hostname to anyone.)
   32. make the tunnel, point the hostname at it, and run it as a service (to do, recorded not run under --prefix)
       # runs lib/cloudflare_tunnel.sh up; the token comes from /etc/sirven/cloudflare-api-token or from the environment of this one command, and is never put on a command line.
       # it makes a tunnel named sirven-agent-<this machine's name>-<random> in account 0123456789abcdef0123456789abcdef, managed from this machine (the dashboard cannot widen it),
       # makes the account sirven-cloudflared for the service (a system account: no shell, no home) unless it is already there and is sirven's own, keeps the tunnel's credentials in /etc/sirven/cloudflared-credentials.json
       # and its config in /etc/sirven/cloudflared.yml (both owned by that account alone, mode 0600), points agent.example.org at it with an alias record,
       # writes /etc/systemd/system/sirven-cloudflared.service and starts it. it records each of these in /var/lib/sirven/cloudflare-tunnel.json as soon as it exists, and refuses with nothing changed if there is no token, no cloudflared, no systemd, or a record at agent.example.org that is not ours.
       # the service it starts runs: cloudflared --no-autoupdate --config /etc/sirven/cloudflared.yml tunnel run   (as sirven-cloudflared.service, run by the account sirven-cloudflared that this step makes: no shell, no home, the only account that can read the credentials and the config; under systemd's sandboxing; it only dials out)
       $ bash <prefix>/var/lib/sirven/package/lib/cloudflare_tunnel.sh up --marker <prefix>/var/lib/sirven/cloudflare-tunnel.json --config <prefix>/etc/sirven/cloudflared.yml --credentials <prefix>/etc/sirven/cloudflared-credentials.json --unit <prefix>/etc/systemd/system/sirven-cloudflared.service --service sirven-cloudflared.service --service-account sirven-cloudflared --user agent --hostname agent.example.org --account 0123456789abcdef0123456789abcdef --token-file <prefix>/etc/sirven/cloudflare-api-token
   33. remove the used API token file, if one was saved (already done)
       $ rm -f <prefix>/etc/sirven/cloudflare-api-token
     note: the agent client connects with: ssh -o ProxyCommand='cloudflared access ssh --hostname %h --service-token-id <token> --service-token-secret <secret>' agent@agent.example.org
