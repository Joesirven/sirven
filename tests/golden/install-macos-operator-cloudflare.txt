service user
     note: dscl, not sysadminctl -addUser: that one wants a password, and this account never has one.
   12. create the service user agent, hidden, not an administrator (to do, recorded not run under --prefix)
       $ dscl . -create /Users/agent
       $ dscl . -create /Users/agent UserShell /bin/zsh
       $ dscl . -create /Users/agent RealName 'sirven agent'
       $ dscl . -create /Users/agent UniqueID 601
       $ dscl . -create /Users/agent PrimaryGroupID 20
       $ dscl . -create /Users/agent NFSHomeDirectory <prefix>/Users/agent
       $ dscl . -create /Users/agent Password '*'
       $ dscl . -create /Users/agent IsHidden 1
       $ dscl . -create /Users/agent GeneratedUID "$(uuidgen)"   # only when the directory service gave none
       $ createhomedir -c -u agent
       $ chmod 0700 <prefix>/Users/agent
       # if any command fails, an account this step started is deleted again: dscl . -delete /Users/agent
   13. confirm agent is not in the admin group (to do, recorded not run under --prefix)
       $ id -nG agent   # must not list admin
   14. create the SSH folder for agent (to do, recorded not run under --prefix)
       $ install -d -m 0700 -o agent -g staff <prefix>/Users/agent/.ssh
   15. create an empty authorized_keys file (to do, recorded not run under --prefix)

   17. add the public key of your agent client (owner, by hand)

transport: cloudflare tunnel
     note: no hostname is named, so agent.example.org stands in. a real apply needs --cloudflare-hostname (a name in a zone of your own that nothing uses yet) and --cloudflare-account.
     note: warning: until you put cloudflare access in front of agent.example.org (an owner step below), anyone on the internet can reach that hostname, and only the SSH keys of agent stand in the way. do that before you give the hostname to anyone.
     note: the tunnel routes exactly one hostname, agent.example.org, to this machine's SSH server (ssh://localhost:22), whatever the level; every other name gets 404. no other port, no private network route.
   25. give the installer one Cloudflare API token, once (owner, by hand)
       Cloudflare dashboard, My Profile, API Tokens: create a token with the permissions Account, Cloudflare Tunnel, Edit and Zone, domain name records, Edit (and Zone, Zone, Read, unless you give the zone number in SIRVEN_CLOUDFLARE_ZONE_ID), limited to your one account and the one zone of agent.example.org. never a token that can do anything else.
       hand it over one of two ways, and it is the only interactive step:
         in a file, the safer way and the one to use first: save it as /etc/sirven/cloudflare-api-token, owned by root, mode 0600, with one name only (no hard link) and no extra access control list; it is removed after the tunnel is made, so give it again to take the tunnel away. this is the only way that never puts the token in an environment.
         in the environment: set SIRVEN_CLOUDFLARE_API_TOKEN in your shell and run sudo --preserve-env=SIRVEN_CLOUDFLARE_API_TOKEN. sudo allows that only when its policy does. the installer takes the token out of its environment at once and hands it only to the steps that need it, but it cannot scrub the block of the environment it was started with: root can still read it in /proc/<installer process number>/environ until the installer ends.
   26. put cloudflare access in front of the hostname, with a service token (owner, by hand)
       cloudflare dashboard, access, applications: add agent.example.org as a self-hosted application.
       policy action: service auth, allowing only a new service token for your agent client.
       do not add email code login or any other login method.
       (until you do, the hostname is reachable by anyone, and only the SSH keys of agent stand in the way. do this before you give the hostname to anyone.)
   27. make the tunnel, point the hostname at it, and run it as a service (plan only)
       $ bash /var/lib/sirven/package/lib/cloudflare_tunnel.sh up --marker <prefix>/var/lib/sirven/cloudflare-tunnel.json --config <prefix>/etc/sirven/cloudflared.yml --credentials <prefix>/etc/sirven/cloudflared-credentials.json --unit <prefix>/etc/systemd/system/sirven-cloudflared.service --service sirven-cloudflared.service --service-account sirven-cloudflared --user agent --hostname agent.example.org --account \<your\ account\ number\> --token-file <prefix>/etc/sirven/cloudflare-api-token
       not yet: applying to a macos machine is not verified yet; the tunnel service is a systemd unit, which only linux has
     note: the agent client connects with: ssh -o ProxyCommand='cloudflared access ssh --hostname %h --service-token-id <token> --service-token-secret <secret>' agent@agent.example.org
